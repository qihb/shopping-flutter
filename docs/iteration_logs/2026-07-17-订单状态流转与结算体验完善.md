# 2026-07-17 订单状态流转与结算体验完善

## 本次目标

在上一阶段已经打通“加入购物车 -> 提交订单 -> 在我的页面看到订单结果”最小闭环之后，这一轮继续把交易链路往真实电商体验推进一小步，重点补齐：

- 购物车里的删除、清空和加入后的反馈提示
- 提交订单前的确认页与地址展示
- 地址管理页与默认地址切换
- 订单状态从字符串展示进一步收拢为枚举，并补一条最小状态流转链路
- 订单详情页与对应测试覆盖

这一阶段的重点不是一次性做复杂架构，而是让“订单”和“地址”开始形成更清晰、可演示、可测试的数据关系。

## 本次实现功能

### 1. 购物车交互进一步完善

购物车页在原有数量增减和提交订单的基础上，又补了几项更接近真实使用场景的交互：

- 支持删除单个商品
- 支持一键清空购物车
- 底部导航的购物车图标会显示角标数量
- 商品加入购物车后会弹出 `SnackBar` 提示

这几项能力都放在 `MainTabPage` 统一处理，再通过回调传给 `CartPage`，方便继续沿着“父组件持有状态，子组件负责展示与发出事件”的学习路径推进。

### 2. 补上订单确认页，形成更完整的结算承接

这次没有直接从购物车瞬间生成订单，而是在中间补了一个 `OrderConfirmPage`，让流程变成：

1. 购物车点击“提交订单”
2. 进入订单确认页
3. 展示当前默认收货地址、商品清单和应付金额
4. 点击“确认支付”后再生成订单

这样做的意义是把“购物车”和“订单生成”之间多加了一层清晰承接，后续如果想继续补支付方式、配送方式、优惠信息，也有了自然的落点。

### 3. 地址管理开始和下单流程串起来

“我的”页现在不只是展示默认地址，还能进入地址管理页，并支持切换默认地址。

### 4. 订单状态正式收拢为枚举，并补最小状态流转

订单模型 `OrderRecord` 这次从“只有展示用途的状态文案”进一步演进为更明确的数据模型：

- 新增 `OrderStatus` 枚举
- 用扩展方法统一管理状态文案、下一状态和是否可推进
- `OrderRecord` 提供 `nextStatusLabel`、`canAdvanceStatus` 和 `advanceStatus()`

这一步很重要，因为它把状态相关规则从页面文案里抽离了出来。对于后续继续补按钮显隐、列表筛选、详情页动作区来说，模型会更稳定。

## 当前涉及的 Flutter / Dart 知识点

### 1. `enum` + extension：把状态规则集中管理

这次把订单状态写成 `enum`，再用扩展方法统一维护标签、下一步状态和判断逻辑。

学习要点：

- `enum` 很适合表达有限且稳定的一组状态
- extension 可以把“和状态强相关的行为”组织到一起
- 这样比在页面里散落多个字符串判断更安全，也更容易维护

### 2. `Navigator.push` + 中间承接页：从购物车过渡到订单生成

订单确认页的加入，让流程不再是“点击按钮就立即生成订单”，而是先进入一个独立页面确认信息。

学习要点：

- `Navigator.push` 可以先类比成“从当前页进入下一层流程页”
- 把复杂流程拆成多个页面，比把所有逻辑堆在一个页面里更容易理解

### 3. 状态提升与共享数据源

地址切换后能同步影响个人中心和订单确认页，是因为这些页面没有各自保存独立副本，而是由 `MainTabPage` 统一持有状态。

学习要点：

- 父组件统一持有共享数据，子组件通过参数展示内容
- 子组件通过回调把操作意图交还给父组件处理
- 这是一条非常典型的 Flutter 入门状态管理路径

### 4. 不可变数据模型与 `copyWith`

购物车条目、地址、订单记录都在继续沿用“不可变对象 + `copyWith`”的更新方式。

学习要点：

- 修改数据时不直接改原对象，而是基于旧对象创建新对象
- 这种写法更容易追踪状态变化，也更适合测试

### 5. Widget 测试在业务流程中的价值

这次测试不是只看页面能否渲染，而是把“地址切换 -> 确认页展示 -> 订单状态推进 -> 页面同步”这种跨页面交互链路也串起来验证。

学习要点：

- Widget 测试很适合验证 Flutter 页面流转和关键用户操作
- 模型单测和页面测试组合使用，能同时覆盖规则正确性和交互正确性

## 学习备注

这一阶段非常适合重点理解两个问题：

- 什么逻辑应该放在模型里，而不是写死在页面里
- 什么数据应该由外层统一持有，而不是在多个页面里各存一份

如果你有前端经验，可以这样类比：

- `OrderStatus` 像是把订单流程里的状态常量和规则集中收口
- `MainTabPage` 更像页面级共享状态容器
- `OrderConfirmPage`、`OrderRecordPage`、`OrderDetailPage` 组成了一条更完整的交易后链路
