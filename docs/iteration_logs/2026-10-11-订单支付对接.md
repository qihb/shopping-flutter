# 2026-10-11 订单 + 支付对接服务端

## 本次目标

完成四步对接计划的第 4 步（最后一步）：把订单与支付链路从本地桥接模型驱动切换到 spring-shop 服务端实现，打通「登录 → 加购 → 下单 → 支付 → 订单状态流转」的完整购物闭环。

## 本次实现功能

### 订单域数据层（新增）

- `OrderService` 对接 4 个订单接口：
  - `GET /api/orders`：`fetchOrders({current})` 拉取订单列表，固定 `size=50` 单页拉取，客户端按状态过滤
  - `POST /api/orders`：`createOrder({addressId, remark})`，备注用 Dart 3.8 null-aware map entry（`'remark': ?remark`）实现「不传不下发字段」
  - `POST /api/orders/{orderNo}/confirm`：确认收货
  - `POST /api/orders/{orderNo}/cancel`：取消订单（服务端回滚库存）
- 订单模型快照化：`OrderVO` / `OrderItemVO`（下单后的商品信息全部为服务端快照），`OrderStatus` 枚举 6 种状态 + `orderStatusFromCode` 未知状态码兜底为待付款（动作集合最保守）
- 新增通用金额格式化 `amountLabel(double)`：整数省小数（`¥89`）、非整数两位小数（`¥19.90`），订单与支付域共用

### 支付域（服务端模拟网关落地）

- `PayService.mockPay` 对接 `POST /api/pay/{orderNo}/mockPay`，返回 `PayResultVO`（订单号、金额、状态、支付时间）
- 新增 `RemotePayGateway implements PaymentGateway` 替换本地 `MockPaymentGateway`：支付请求落到服务端模拟网关，成功/业务失败/其它异常分别收敛为统一 `PaymentResult`
- 保留 `PaymentGateway` 抽象与真实支付骨架（Alipay tobias 链路、微信占位），`PaymentServiceFactory` 的服务端模拟模式改为两渠道共用同一个 `RemotePayGateway` 实例
- `PaymentRequest` 调整：`orderId` 必填（支付对象是订单号），金额/标题改为可选

### 状态编排层

- `OrderNotifier` 重写：沿用购物车/地址已验证的模式——
  - `attachAuth` 登录态联动（登录拉取、登出清空、恢复会话时同步）
  - `createOrder` 成功返回订单号并静默刷新，失败返回 `null` 并记录可读错误
  - `payOrder` 把 `PaymentResult` 翻译成 `bool`，失败透传网关提示，不刷新列表
  - `confirmReceipt` / `cancelOrder` 走 `_mutate` 模式：变更成功后静默刷新（不展示加载态）
- 状态流转以服务端为准：待付款 → 待发货由服务端 `mockPay`「一次到位」；待收货 → 已完成需用户确认收货；待付款 → 已取消由用户取消

### 页面接线

- 订单确认页：直接消费服务端 `CartItemVO` + `AddressVO`，支付说明改为「服务端模拟支付网关」；下单时无地址进入引导新增地址
- 订单记录页 / 订单详情页：改为 `OrderVO` 驱动，删除泛化的「推进状态」，动作收敛为三个回调（续付 / 确认收货 / 取消），续付不再重开订单确认页、直接按默认渠道支付
- 我的页：订单状态概览固定 4 个主流程入口（待付款/待发货/待收货/已完成），已取消/已退款为终态不占入口；最近订单卡片展示订单号、实付金额、收货地址与商品快照
- 主 Tab：下单编排（下单 → 支付 → 成功清勾选购物车 → 切「我的」）、订单动作编排（续付成功切「我的」、确认收货/取消带 toast）
- `CartNotifier.selectedItems` 直接返回 `List<CartItemVO>`（已勾选且有效），删除桥接转换层

### 清理旧桥接模型

删除 `CartItem`、`OrderRecord`、`UserAddress`、`MockPaymentGateway` 及对应测试文件，订单/购物车/地址全部以服务端 VO 为唯一数据形态。

## 当前涉及的 Flutter / Dart 技术点

- **dio 网络层**：统一 `parseResultData` 解包 `Result<T>`，业务失败抛 `ApiException(message)`
- **Dart 3.8 null-aware 元素**：`'remark': ?remark` 让可选请求体字段「不传即不存在」
- **Record 多值返回**：测试装配函数返回 `(_TestAppWithGateways)` 具名元组、状态测试 fixture 返回五元组替身集合
- **enum + extension**：`OrderStatus` 状态文案/动作集合（`canPay`、`canConfirmReceipt`）挂在 extension 上，未知码兜底收敛在顶层转换函数
- **mockito 替身**：`MockSpec` 登记集中生成；命名参数匹配 `anyNamed`、请求捕获 `captureAny`
- **有状态假服务端测试模式**：内存快照 + 最小状态机模拟服务端行为，替身之间通过 `markPaid` 联动，保证「支付成功 → 订单待发货」的真实链路顺序
- **支付网关抽象 + 工厂**：同一 `PaymentService` 收银台接口下，服务端模拟 / 真实支付双模式可切换，为跨端真实支付留位
- **金额格式化统一收敛**：`amountLabel` 一个口径覆盖订单、支付、购物车文案

## 实现说明

- 列表接口不做分页 UI：`size=50` 单页拉取后客户端按状态过滤，当前订单量级下最简单可靠；接口参数 `current` 已预留扩展位
- 复付流程简化：待付款订单在记录页直接按默认渠道发起支付，不再重开订单确认页重选地址/渠道（服务端已持有地址快照，重选反而会改动订单内容）
- 支付域保持 `PaymentGateway` 抽象是因为跨端支付（Apple Pay / 支付宝 / 微信）是后续第一优先级的原生能力接入点，`RemotePayGateway` 只是该抽象下的一个服务端模拟实现
- 订单详情页不独立持有序列化状态，watch `OrderNotifier` 按 `orderNo` 定位最新数据，列表/详情天然同步
- `GET /api/orders/{orderNo}` 本轮未接入：列表与详情共用字段，等详情出现差异字段再接
